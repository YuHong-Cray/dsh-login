# dsh-login 方案：普通用户自助添加模型提供方（直接填入模型公司的 API key）

> 状态：待评审。本方案只覆盖 dsh-login 插件（纯 Node.js，无构建），不改动 DSH 核心（/deepseek-harness）。

## 1. 背景与现状

### 1.1 现有模型配置通道

| 通道 | 谁可用 | 条件 | 现状 |
| --- | --- | --- | --- |
| DSH 原生「设置 → 模型」页（用户实例内） | 用户本人 | 浏览器必须是 **loopback**（DSH 客户端策略 `isLoopback`，`packages/client/connection`；非 loopback 页面 settings/credentials 持久化被禁用，页面报 *settings are unavailable in this browser*） | 可用，但 LAN 用户（如 `192.168.x.x:3100`）被客户端策略拦截，**不可用** |
| 管理员「用户管理 → 模型」（hub `/dsh-login/users/models?user=X`） | 仅管理员 | 无 | 可用；hub 用 inner cookie 对该用户实例自己的 `/api` 执行 `settings/mutate` + `credentials/set` |

### 1.2 问题

1. **LAN 普通用户无法自助**：DSH 有意的非 loopback 禁写策略使原生模型页对 LAN 用户整体不可用，添加/更换 API key 必须找管理员代劳；
2. **管理员代配置页是控制台风格**：provider 标识 / api / baseURL / 模型 ID 全手工填写，面向技术用户，不是给普通用户直接用的界面。

### 1.3 目标

在用户自己的实例上提供一个**自助「模型管理」页**：

- 普通用户登录自己的实例后，选择一个**模型公司**（DeepSeek、OpenAI、Anthropic、月之暗面、智谱……），**直接粘贴该公司官网签发的 API key**，即可完成提供方添加；
- 内置 pi-ai 目录的常见公司**只需填 key**（baseURL/协议/模型目录全部来自 pi-ai 内置目录）；
- 目录外的公司（自建/中转/OpenAI 兼容网关）走「自定义」表单；
- 支持删除提供方、设为默认模型、（P2）从端点拉取可用模型；
- 全程只写**该用户自己** `DSH_HOME` 下的 `settings.yaml` / `.credentials.yaml`。

非目标：不改 DSH 的 `isLoopback` 安全策略；不做跨用户/跨实例的批量配置（那是管理员页的职责，保留）。

## 2. 总体方案

### 2.1 位置：用户实例的 `/dsh-login/models`（instance 模式新增路由）

| 备选 | 结论 | 理由 |
| --- | --- | --- |
| **A. 实例侧自助页（本方案）** | ✅ 采用 | 用户日常就在自己的实例；实例内置 cookie（30 天）已是完整认证；不依赖 hub 在线（hub 重启不影响）；写目标是本进程自己的 loopback API，无跨进程信任；与实例「账户中心」对称 |
| B. hub 侧 `/dsh-login/my-models`（hub 经 `instanceRpc` 代写用户实例） | 备选 | 也能工作（复用 hub 的 instanceRpc），但多一跳网络、依赖 hub 在线、用户要回到 3080 操作；P1 不需要 |
| C. 放宽 DSH `isLoopback` 策略让 LAN 直接用原生页 | ❌ 否决 | 改 DSH 核心安全策略，影响所有部署；风险与工作量远大于插件加一页 |

### 2.2 认证与权限

- 页面门禁 = 实例现有 `decide()`：携带**本实例 authority 的有效 inner cookie** 才放行（cookie 签名受众绑定 `Host:port`，只有该用户自己浏览过其实例的浏览器持有；管理员「以该用户进入」时管理员浏览器也持有——与现有信任模型一致，README 已声明该限制）。
- **不授予新权限**：门禁对 `/api/*` 本就只要求 `innerOk`，cookie 持有人今天就能直接调 `settings/mutate`、`credentials/set`。本页只是把这组**受 DSH 校验的写入接口**包一层普通用户能看懂的表单。
- 所有 POST 增加 **Origin 同源校验**（与现有管理页一致）。

### 2.3 写入路径（复用既有机制，不新造轮子）

实例模式插件启动时已读入 browser-session 签名密钥（`applyInstance` 里的 `readInnerSecret(ctx.credentials)`），端口在 `cfg.port`。新增 `selfRpc(port, method, args)`：

- 为本实例 loopback authority（`127.0.0.1:<cfg.port>`）铸造 inner cookie（`mintInnerCookie`），
- POST `http://127.0.0.1:<port>/api/<method>`，body 为 `{type:'client-request', rpcId, method, payload:{args}}`，
- 与 hub 的 `instanceRpc`（index.js 967–991 行）**完全同一模式**，只是目标是自己的进程。

经 DSH 自己的 `/api` 写入 ⇒ settings 服务校验 schema、审计、**热加载**（管理员通道已实测：保存后模型目录立即生效，无需重启实例）。

### 2.4 数据模型（与 DSH 原生页、管理员页一致）

- 提供方 profile：`settings/mutate` → `ns: "llm-pi-ai"`，`ops: [{op:'set', path:['providers', <id>], value}]`
  - **内置目录 route**（pi-ai 认识的 id）：`value = {apiKeyEnv: "<ID>_API_KEY"}` 即可（api/baseURL/模型全部取目录默认；可选 `models` 覆盖）；
  - **自定义 route**：`value = {apiKeyEnv, api, baseURL, models:[{id,name?}]}`；
- API key：`credentials/set {ref: "<ID>_API_KEY", value}`（写入该用户 `.credentials.yaml`，0600；ref 命名规则与 `providerRefName` 一致）；
- 默认模型：`settings/mutate` → `ns: "agent-default-model"`，set `provider`/`model` + `unset reasoningEffort`（避免旧 effort 残留导致 UNSUPPORTED_REASONING_EFFORT，管理员页同一写法）；
- 注意区分：实例模板用 `llm-deepseek: {models: []}` 隐藏的是 **dsh-base 的 `deepseek-official`** 目录；用户在这里添加 DeepSeek 走的是 **pi-ai 的 `deepseek` route**（`llm-pi-ai` 命名空间），两者不冲突，模型选择器里显示为 `deepseek`。

## 3. 页面与交互设计（`/dsh-login/models`，服务端渲染，深色主题，沿用 `account-page.js` 的 THEME）

```
│ [保存]                                                     │

```

要点：

1. **内置预设**：route id **固定不可改**（就是 pi-ai 目录里的 id，key 的 ref 由它派生）；baseURL/协议/模型来自目录，页面上只展示为「目录默认」；用户唯一必填是 **API key**；
2. **自定义预设**：route id（小写字母/数字/连字符，2–32）+ 显示名（可选）+ baseURL（必填，http(s)）+ 协议（下拉，默认 `openai-completions`）+ 至少 1 个模型（P1：模型 ID 文本框，可多行逗号分隔；P2：拉取勾选）+ API key（可选：留空 = 该 route 走提供方自带鉴权/环境发现，与 DSH 原生语义一致）；
3. **key 只进不回**：密码框输入；保存失败重渲染时**不回显** key；页面 HTML、日志均不含 key；
4. 已配置列表的 **key 状态点**：来自 `credentials/describe` 的 `configured`（绿点/红点，与 DSH 原生页同款语义）；
5. 删除带确认（浏览器 confirm 即可，量级不需要弹层）；若被删提供方是当前默认，见 §9 开放问题。

## 4. 接口设计

所有路径在 **实例** 的 `/dsh-login` 前缀下；门禁同现有 `decide()`（inner cookie）；POST 一律 Origin 同源校验；成功 GET/HTML 用 303 回带 `?ok=...`（与管理员页一致），动作类用 JSON。

| 路径 | 方法 | 入参 | 行为 / 出参 |
| --- | --- | --- | --- |
| `/dsh-login/models` | GET | — | 读 `settings/describe`（providers + agent-default-model）+ `credentials/describe([<ID>_API_KEY…])`（key 状态）→ 渲染整页 |
| `/dsh-login/models` | POST | 表单/JSON：`preset`（内置 route id）或自定义字段集（`providerId, displayName?, api, baseURL, models, apiKey, setDefault?`） | 校验 → `settings/mutate`（profile）→ `credentials/set`（若填 key）→（若 setDefault）`agent-default-model` → 303 回 `?ok=` |
| `/dsh-login/models/delete` | POST | `{id}` | `credentials/unset <ID>_API_KEY`（ref 存在时）→ `settings/mutate` unset `providers.<id>`；两步皆幂等，**先 key 后 profile**（与 DSH 原生 `removeProviderProfile` 同一顺序：第二步失败时 provider 行仍在页面上，操作可安全重试） |
| `/dsh-login/models/default` | POST | `{provider, model}` | `agent-default-model` set provider/model + unset reasoningEffort |
| `/dsh-login/models/fetch` | POST（P2） | `{baseURL?, api?, apiKey, provider?}` | 服务端调 `llm/discoverModels`（draft 语义：route 尚不存在也能问；`provider` 指定目录 route 时适配器直接从注册表回答，免网络）→ `{models:[{id, name?}]}` |

**写序语义（与 DSH 原生 CustomProviderCard 对齐）**：

1. profile 先落（`settings/mutate`，`expectedRevision: undefined`——单用户自己的设置，无并发编辑场景，与管理员页一致）；
2. key 后落（`credentials/set`）；key 失败时 profile 已存在，重试**只重发 key**（页面保留「profile 已写入」状态位，避免重试触发重复 set 造成 revision 冲突）；
3. 错误文案必须指明卡在哪一步（profile 校验失败 / key 写入失败 / 默认模型写入失败），key 本身永不回显。

### 4.1 服务端校验（P1 规则，镜像 DSH 原生）

| 字段 | 规则 |
| --- | --- |
| 内置 `preset` | 必须在预设表内（表由代码维护，route id 固定） |
| 自定义 `providerId` | `^[a-z][a-z0-9-]{1,31}$`（与管理员页 `PROVIDER_ID_PATTERN` 一致；不得与已配置 id 撞名） |
| `api` | 协议白名单（§3.2 下拉全集）；留空时内置=目录默认，自定义=`openai-completions` |
| `baseURL` | `^https?://\S+$`，≤200 字符 |
| `models` | ≥1 行；id 非空 ≤200 且唯一；显示名可选 ≤200 |
| `apiKey`（内置必填 / 自定义可选） | 去空白后非空；`^[\x21-\x7E]+$`（可打印 ASCII、无空格）；不得形如 `NAME=value`（`^[A-Z][A-Z0-9_]*=[^=]`）；不得被成对引号包裹；≤4096（规则与 DSH 原生 `apiKeyFailure` 保持一致，注释里互相引用） |
| `setDefault` 的 model | 必须在本次写入的 models 内（或已配置 models 内） |

## 6. 安全分析

1. **访问控制**：页面 = 实例 inner cookie 门禁。该 cookie 的持有人今天已可直调实例 `/api/*`（门禁对 /api 只要求 `innerOk`），页面**不扩大任何权限**，只是把既有 API 做成表单。管理员「以该用户进入」后可见本页，属于 README 已声明的既有信任模型限制，非新增面。
2. **写入范围**：RPC 目标是本实例自己的 loopback `/api`，落盘只在该用户 `DSH_HOME`（`settings.yaml` + `.credentials.yaml`，0600）；hub 与其他用户零接触。隔离性与管理员通道等同。
3. **key 生命周期**：入站（HTTPS/LAN 内的 POST body）→ 内存 → `credentials/set` 落 0600 文件；不回显、不进 HTML、不进日志；`credentials/describe` 只返回 `configured/writable` 状态（DSH 侧 redactSecrets 已保证）。
4. **CSRF**：全部 POST 做 Origin 同源校验（同现有管理页）；页面与请求同源。
5. **出站请求（SSRF 面）**：用户提供的 baseURL 会让**该用户的实例进程**对其发起 HTTP（拉取模型 + 之后的真实推理）。注意：这一能力类别**今天已存在**——管理员通道与 loopback 原生页同样允许任意 baseURL。本页只把决定权从管理员移到用户，信任边界（同机同主机）不变；推理流量本来就要出站到用户选的端点，拦截没有意义。若仍希望收紧，可只对 `fetch`（唯一由插件主动发起的配置时探测）加内网网段拒绝列表——列为 P3 可选加固，不阻塞。
6. **升级兼容**：实例内的插件是 provisioning 时的 `file:` 拷贝；存量实例在重新 provisioning 前没有新页面（与现有插件升级行为一致，README 已说明）。hub 无需重启；新登录用户的实例自动拿到新页。
7. **并发**：单用户对自己的设置编辑，写用 `expectedRevision: undefined`（同管理员页）；不引入 revision 围栏的复杂度。

## 7. 测试计划

1. **单元**（`node --test`）：
   - 预设表完整性（id 唯一、api/baseURL 非空、协议在白名单内）；
   - `validateModelConfig` 扩展：内置 preset 分支（无 key 拒绝、key 规则全矩阵：空/空白/含空格/引号包裹/`NAME=value`/超长/合法）、多模型去重、自定义 id 撞名、baseURL 协议限制；
   - `deleteProviderOps` / `setDefaultOps` 的 ops 序列（含 unset reasoningEffort）。
2. **集成**（假宿主 webServer + stub `/api` 路由，仿 `test/gate.test.mjs` 的假宿主手法；instance 模式不依赖 MySQL，测试更轻）：
   - 无 cookie GET `/dsh-login/models` → 302 回 hub 登录页；
   - 有效 inner cookie GET → 200，含已配置 provider 与默认模型行；
   - POST 添加内置 preset（仅 key）→ 断言按序发出 `settings/mutate`（value 只含 `apiKeyEnv`）+ `credentials/set`；
   - POST 添加自定义（全字段 + 多模型）→ 断言 profile 完整；
   - POST key 格式错误 → 400，响应不含 key 原文；
   - POST delete → 断言 unset 序列；再删一次幂等；
   - POST default → 断言 `agent-default-model` ops 含 `unset reasoningEffort`；
   - POST fetch（P2）→ 断言 `llm/discoverModels` 收到 draft 字段（apiKey 不存储、仅透传）；
   - 非同源 Origin POST → 403。
3. **手工 E2E**（本部署）：注册新用户 → LAN IP 登录其实例 → `/dsh-login/models` 添加 DeepSeek 真实 key → GUI 模型选择器出现 `deepseek` 模型 → 新建会话成功对话；再经 hub「以该用户进入」与管理员「用户管理 → 模型」交叉核对同一份 `settings.yaml`。

## 10. 实现补充：管理员逐人审批开关（已实现）

本方案原设计让用户在自己的实例里自助增删改 provider，**未设权限闸门**。实际部署要求「普通用户能否设置模型参数」由管理员逐人批准，落地形态如下（运维细节见 README 的「模型自设审批」一节）：

- 账号表新增 `model_self_service TINYINT(1) NOT NULL DEFAULT 0`（`ensureTable()` 自动 ALTER 老表，**默认禁止**）；
- hub「用户管理」表格新增**自行设置模型**列与「允许 / 禁止自行设置模型」按钮（`POST /dsh-login/users/model-policy`）——**点「允许」即为批准**，不引入逐次「申请 → 审批」队列；
- 决定同时写账号表列与该用户 `DSH_HOME/dsh-login-model-policy.json`（新模块 `lib/model-policy.js`）：实例**每次请求现读**，因此改开关**无需重启实例、不依赖 hub 在线**；文件缺失/损坏按**禁止**处理（fail closed，保证升级后默认仍是禁止）；
- 未获批准时**整条接口关闭**：`GET /models` 返回 403 的「管理员已关闭」页（不列出 provider、不渲染表单），`POST /models`、`/models/delete`、`/models/default`、`/models/models-of` 一律 **403**——服务端强制，不只是隐藏控件；账户中心也不再提供「我的模型」链接；
- 管理员代管通道（`/dsh-login/users/models`）**不受**该开关影响：无论是否批准用户自助，管理员都能替用户配置；
- 边界说明：该开关约束的是本插件自助页，不是针对实例所有者的硬沙箱（实例以 root 运行、其所有者本就能触碰同一份 settings/credentials 与实例 `/api`，见 README 安全说明的既有信任模型）。
